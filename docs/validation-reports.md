# Validation Reports

Validation reports let DevGrimoire understand test, build, lint, typecheck, health-check, and workflow validation results as first-class project signals. They should help agents and humans see whether a todo is actually ready for review or done, and turn failures into safe follow-up work.

## Goals

- Attach validation results to projects, todos, commits, releases, workspaces, and workflow runs.
- Show the latest validation state directly on todo detail and review/done flows.
- Parse common tool outputs into a compact structured result.
- Allow failed reports to create reviewable bug-todo proposals with repro context.
- Keep logs short, masked, and safe for agents to read.

## Non-goals

- Do not store unlimited raw test logs.
- Do not auto-create bug todos without an explicit setting or user/agent confirmation.
- Do not store secrets, env dumps, tokens, or full command environments.
- Do not replace CI systems; DevGrimoire stores and interprets their results.

## Entity sketch

```ts
type ValidationStatus = 'passed' | 'failed' | 'warning' | 'skipped' | 'running' | 'unknown';
type ValidationKind = 'test' | 'build' | 'lint' | 'typecheck' | 'health' | 'security' | 'workflow' | 'custom';

interface ValidationReport {
  _id: ObjectId;
  projectId: ObjectId;
  status: ValidationStatus;
  kind: ValidationKind;
  source: {
    type: 'agent' | 'cron' | 'workflow' | 'ci' | 'user' | 'mcp';
    name?: string;
    runId?: string;
  };
  target: {
    todoId?: ObjectId;
    commitSha?: string;
    workflowRunId?: ObjectId;
    releaseId?: ObjectId;
    workspaceId?: ObjectId;
  };
  command?: string;
  summary: string;
  parser?: string;
  metrics?: {
    total?: number;
    passed?: number;
    failed?: number;
    skipped?: number;
    durationMs?: number;
    exitCode?: number;
  };
  failures: ValidationFailure[];
  logExcerpt?: string;
  artifactRefs?: ValidationArtifactRef[];
  createdBy?: ObjectId;
  createdAt: Date;
}

interface ValidationFailure {
  name: string;
  file?: string;
  line?: number;
  message: string;
  stackExcerpt?: string;
  reproductionHint?: string;
}

interface ValidationArtifactRef {
  type: 'junit' | 'coverage' | 'log' | 'screenshot' | 'other';
  attachmentId?: ObjectId;
  url?: string;
  label: string;
}
```

## Secret and log safety

Before storing `summary`, `logExcerpt`, failures, or artifacts generated by parsers:

- Mask common token patterns (`Bearer …`, API keys, JWTs, private keys, passwords).
- Truncate log excerpts to a configurable size, for example 16 KiB per report.
- Prefer first/last relevant failure snippets over full stdout/stderr.
- Store command name and args only after stripping inline env assignments and secret-looking flags.
- Never persist decrypted DevGrimoire secrets or full process environments.

## Parser MVP

Start with line-oriented parsers and a generic fallback.

| Parser | Inputs | Structured output |
| --- | --- | --- |
| `generic_exit_code` | command, exit code, stdout/stderr | status, duration, excerpt |
| `npm_test` | npm/jest/vitest style output | test counts, failed test names |
| `pytest` | pytest summary | counts, failing node ids/files |
| `tsc` | TypeScript compiler output | file/line diagnostics |
| `eslint` | stylish/json output | file/line diagnostics |
| `docker_compose_health` | compose ps/health output | service health summary |

Parsers should be best-effort. Unknown output still creates a report with status and safe excerpt.

## API sketch

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/validation-reports?projectId=&todoId=&status=&kind=` | List reports |
| `POST` | `/api/validation-reports` | Add structured or raw validation result |
| `GET` | `/api/validation-reports/:id` | Read a report |
| `POST` | `/api/validation-reports/:id/propose-bug-todo` | Create a reviewable bug-todo proposal from failures |
| `GET` | `/api/todos/:id/validation-summary` | Latest validation state for todo detail |

`POST /api/validation-reports` should accept either already structured fields or raw output plus parser hints:

```json
{
  "projectId": "...",
  "target": { "todoId": "..." },
  "kind": "test",
  "source": { "type": "agent", "name": "openclaw-cron" },
  "command": "npm test",
  "exitCode": 1,
  "durationMs": 12000,
  "stdout": "...",
  "stderr": "...",
  "parser": "npm_test"
}
```

The backend masks/truncates raw fields before persistence.

## MCP and agent tools

Read/write tools should be explicit and scope-aware:

- `validation_report_add` — write, project/todo scoped, stores masked report.
- `validation_report_list` — read, filters by project/todo/status/kind.
- `todo_validation_summary` — read, returns latest report summary for a todo.
- `validation_report_propose_bug_todo` — write, creates draft/proposed todo from failures.

Agents should attach validation reports after running tests/builds and mention the report id in todo comments or run logs.

## Todo integration

Todo detail should show:

- Latest validation status badge.
- Last successful validation time.
- Last failed validation summary and top failures.
- Linked validation history.
- Button/action to create bug todo proposal from a failed report.

Review/done flow should warn when:

- No validation report exists for the todo and the todo changed code.
- Latest report failed.
- Latest report is older than relevant code changes or workflow runs.

## Bug-todo proposal flow

1. User/agent opens a failed validation report.
2. DevGrimoire extracts top failures and reproduction hints.
3. A draft bug todo is generated with:
   - title from failing suite/file/command
   - compact masked log excerpt
   - target links to original todo/report/commit
   - suggested repro command
4. User or allowed agent confirms creation.
5. Original validation report links to created todo.

## Workflow integration

The workflow node `Run validation` should:

- Run an approved command/profile.
- Store a validation report for every run.
- Expose report status as node output.
- Allow conditions to branch on pass/fail/warn.
- Never expose raw secret values in node logs or outputs.

## Acceptance mapping

- **Structured storage:** `ValidationReport` stores test/build/lint/health results attached to project entities.
- **Bug-todo proposal:** failed reports can produce reviewable bug-todo drafts with compact repro context.
- **Todo visibility:** todo summary endpoint and UI badge show latest validation state.
- **Done/review flow:** stale/missing/failed validation can warn before done.
- **Masked logs:** parser and storage layer mask and truncate all raw output.

## Implementation order

1. Add `ValidationReport` schema/service and masking helper.
2. Add generic parser and `POST /api/validation-reports`.
3. Add list/detail endpoints and todo validation summary endpoint.
4. Add todo detail UI badge/history panel.
5. Add bug-todo proposal endpoint.
6. Add MCP tools and workflow node integration.
7. Add specialized parsers for npm/vitest/jest, pytest, tsc, eslint, and docker compose health.

## Implementation slice — persistence API and MCP tools

The first implementation slice adds a `ValidationReport` backend module with REST and MCP access:

- `POST /api/validation-reports` creates a report.
- `GET /api/validation-reports?projectId=&todoId=&status=&limit=` lists recent reports.
- `GET /api/validation-reports/todo/:todoId/latest` returns the latest Todo-linked report.
- `GET /api/validation-reports/:id` returns a full report.
- `validation_report_add`, `validation_report_list`, and `validation_report_get` expose the same core flow to MCP agents.

Stored `summary` and `outputSnippet` fields are masked and truncated server-side. This keeps the initial feature safe for cron jobs, agents, and future workflow validation nodes while UI badges, bug-todo proposals, and parser-specific enrichment remain follow-up work.
